# StackMind `feat/v2.0.0` — Review Verdict

**Comparison:** `main` → `feat/v2.0.0`
**Scope:** 110 files changed, +11,710 / −598
**Reviewed:** 2026-07-18

---

## Verdict: 🟡 Strong work, not release-ready as "2.0.0"

The branch delivers two substantial, well-structured new subsystems and is genuinely a major-version leap in *capability*. But it ships under a `2.0.0` banner that the actual package metadata doesn't back up, carries build artifacts that shouldn't be committed, and quietly drops its own coverage gate. Fix the blockers below and this is a clean, confident 2.0.

---

## What's good

- **Real architectural progression.** v1 was a governance/validation runtime; v2 adds a deterministic source→IR **Knowledge Compiler** and an agent-execution **Harness**. This is a coherent, layered design (compile → project → enrich → query → harness → govern), not feature sprawl.
- **Test investment is serious.** ~11 new test files across every new module (registry, compiler frontend, storage, projections, incremental, rename, enricher, knowledge API, harness, CLI integration). Release notes claim 304 tests / 83% coverage.
- **Clean module boundaries.** `validators/knowledge/` and `validators/harness/` are self-contained with clear responsibilities; new CLI surface (`graph`, `harness`) is additive and doesn't disturb existing commands.
- **Documented.** README/PLAN rewritten, plus AGENTS.md, STACKMIND.md, and a release summary. Intent is legible.

## Blockers (fix before calling this 2.0.0)

1. **Version not actually bumped.** `pyproject.toml` still reads `version = "1.2.0"` on the v2.0.0 branch. The "2.0.0" exists only in docs. A release branch must bump the packaged version.
2. **Committed build artifacts.** `validators/harness/__pycache__/*.pyc` are checked in. Remove them and add a `.gitignore` rule — `.pyc` files should never be in version control.

## Concerns (should address, non-blocking)

3. **Coverage gate silently removed.** The diff deletes `addopts = "-v --cov=cli --cov=validators"` from `pyproject.toml`. This drops enforced coverage reporting exactly when the codebase 3×'d in size. If intentional, say why in the commit; otherwise restore it.
4. **New heavy dependencies.** `jedi` and `libcst` are reasonable for static analysis but expand the install/security surface — worth a line in the release notes on why each is needed.
5. **Provenance / velocity claim.** Release notes state all 8 phases (11k+ lines) shipped "in 1 day (single session)" by a multi-agent team. Impressive if accurate, but such volume in one pass warrants extra human review of the compiler's resolve/rename logic and the harness write-back path — the highest-risk areas.

## Recommendation

**Merge after:** (1) bumping the real version string, (2) removing `.pyc` files + adding `.gitignore`. **Before tagging the release,** restore or consciously waive the coverage gate, and give the compiler resolution and harness write-back a focused human read. The engineering is sound; the release hygiene is what's missing.

## Flaws, Gaps & Vulnerabilities (code-level)

Findings from reading `validators/harness/runner.py`, `validators/knowledge/enricher.py`, `validators/knowledge/api.py`, and `cli/lock.py` on `feat/v2.0.0`. Severity is my own estimate.

### 🔴 High

**1. The "write lock" is not actually a lock — TOCTOU race.**
`cli/lock.py:acquire_lock()` does `read_lock()` → check holder → `write_text()`. That's a classic check-then-act with a wide race window: two agents can both read "unlocked" and both write the lockfile, both believing they hold it. There is no atomic primitive (`os.open(..., O_CREAT|O_EXCL)`, `fcntl.flock`, or `os.link`). Since every "governed" write and the enricher cache depend on this, the core concurrency guarantee of the whole governance model is unsound under real parallelism.

**2. The harness cannot apply the code changes it "decides" on.**
Tracing `run_once()` → `_non_report_ops()` → `_apply_ops()`: the only files ever written are `.sync` bookkeeping — inbox archival (`FileMove`), the work-order YAML `log`, review/completion notices to `.sync/inbox/gemma` & `.sync/inbox/claude`, plus the report and events JSONL. The LLM output schema (`harness-output.schema.json`) has fields `status, summary, report_markdown, blockers, modified_files, release_target, …` — **`modified_files` is a list of name strings only; there is no field carrying code/diff/content.** So the "poll → context → LLM → verify → write-back" capstone is an *orchestration/bookkeeping* loop; it does not (and structurally cannot) apply source edits. The release framing oversells what ships.

**3. "Verify" verifies the wrong tree.**
`_validate_staged_state()` copies the project to a tempdir and runs `validate_runtime()` — but the staged copy only receives the bookkeeping writes above, never the LLM's actual code change (see #2). So validation-before-commit attests to a tree that doesn't contain the change it's supposed to be gating.

### 🟠 Medium

**4. Weak secret redaction + privacy-hostile default.**
`enricher.py` sends source excerpts to an LLM, and default `privacy_mode='full'`. Redaction is two regexes: quoted `key/token/secret/password = "…"` and `Authorization: Bearer …`. It misses JSON (`"api_key": "…"`), unquoted env assignments (`AWS_SECRET=…`), PEM/private-key blocks, connection strings, and shape-matched cloud keys. The redaction creates false confidence while real secrets leak to the model by default.

**5. Path traversal in `enricher._read_excerpt`.**
`source_path = project_path.resolve() / rel_path` with no containment check. If `rel_path` is absolute or contains `../`, `Path.__truediv__` escapes the project root, and the file's (partially redacted) contents get read and sent to the LLM. `rel_path` originates from compiled node data, so exploitability hinges on how trusted/tamper-resistant the knowledge graph is — but a `resolve()` + `is_relative_to(project_root)` guard is missing and cheap.

**6. Untrusted source → LLM → filesystem side effects (prompt injection).**
Analyzed source code flows into both the enricher and the harness LLM context. Harness decisions then generate real files (forged-looking review/completion notices routed to other agents' inboxes). Adversarial comments in a scanned repo can steer enrichment output and harness routing. No trust boundary is drawn between "code under analysis" and "instructions to the agent."

**7. `--force` lock steal is unauthenticated + no stale detection.**
Any agent may steal the lock with `force=True`; the lock records `acquired_at` but nothing ever expires a stale lock, so a crashed holder blocks the pipeline until a human intervenes — while a misbehaving agent can silently steal at will. There's no reconciliation of these two opposite failure modes.

### 🟡 Low / correctness & scaling

**8. Full-tree copy every run.** `_validate_staged_state()` does `shutil.copytree(project)` on *each* `run_once()` — O(repo size) per iteration; won't scale to large repos.

**9. Non-atomic `FileMove`.** `_apply_ops()` does `target.unlink()` then `source.rename(target)`; a crash between the two destroys the target with the source not yet moved.

**10. Crude token accounting.** `_estimate_tokens = ceil(len/4)` drives the context-assembly budget; for real tokenizers this can mis-size context enough to overflow or over-truncate what's sent to the model.

**11. Silent failure swallowing.** `_git_output()` (and similar) returns `''` on any error, masking git/environment problems as "no data" rather than surfacing them.

### Recap of release-hygiene issues (from the verdict above)
Version still `1.2.0`; committed `__pycache__/*.pyc`; coverage gate (`--cov`) deleted, so the advertised 83% is now unverifiable in CI.

### Highest-leverage fixes
1. Replace `acquire_lock` internals with an atomic primitive (`O_EXCL` create or `flock`) + a TTL/heartbeat for staleness. (#1, #7)
2. Decide what the harness *is*: either implement real patch application + validate the patched tree, or rename/reframe it as an orchestrator so the docs match reality. (#2, #3)
3. Harden the enrichment egress path: containment-check excerpt paths, strengthen redaction, and make `privacy_mode` default to something safer than `full`. (#4, #5)

## Documentation (`docs/`)

The `docs/` tree has five files, **byte-identical on `main` and `feat/v2.0.0`** — they were never touched by the 110-file v2.0.0 work.

| File | Lines | Covers |
|------|-------|--------|
| `getting-started.md` | 76 | install, `init`/`validate`/`doctor`, project layout |
| `architecture.md` | 204 | engine-vs-instance model, authority hierarchy, invariants, two-repo + `.sync-ref` design |
| `protocols.md` | 398 | D021–D031 protocols, boot/shutdown sequences, work orders, handoff format |
| `cli-reference.md` | 523 | per-command reference for the v1.x command set |
| `migration-guide.md` | 402 | version upgrade guidance |

> Branch note: `main` has since advanced (it now includes a `feat/runtime-integrity-enforcement` merge); `feat/v2.0.0` is **20 commits ahead of `main`** with `main` fully contained in it. The docs are unchanged across both.

**What's good.** For the v1.x product the docs are genuinely strong: the architecture doc's authority model, key invariants (lock serialization, draft→canonical gating, TREE/INDEX drift anchor), and the two-git-repo/`.sync-ref` anchoring are clear; `protocols.md` is precise and even pre-empts the `tree_version` vs `graph_version` naming question.

### 🔴 The v2.0.0 feature surface is entirely undocumented

The v2.0.0 code registers two new CLI command groups that appear **nowhere** in `docs/`:

- **`stackmind graph`** — 10 subcommands: `build, update, watch, query, callers, impact, explain, context, stats, versions`
- **`stackmind harness`** — `run-once`

`cli-reference.md`'s command table stops at the v1.x set (`init, validate, doctor, migrate, shutdown, promote, lock`); `getting-started.md` never mentions the Knowledge Compiler or Harness — the two "pillars" the README and `RELEASE-v2.0.0.md` are built around. The flagship features ship documented only in top-level marketing/release files, not in the user-facing docs. A branch calling itself 2.0.0 has not updated its docs for the release.

### 🟡 Secondary doc issues

- **`graph` naming collision.** Docs already use "graph" for `graph_version`/GRAPH_SIG (SHA-256 of `graphify-out/GRAPH_REPORT.md`, from v1.1.0/D023.3). v2.0.0's `stackmind graph` is a completely different concept (the knowledge compiler). Grepping the docs for "graph" lands on the old meaning — needs disambiguation.
- **`pip install stackmind`** (getting-started, step 1) — confirm the package is actually published under that name, or the first step fails.
- **Possible artifact drift.** Docs describe `graphify-out/GRAPH_REPORT.md` as a live artifact; I did not see it produced by the v2.0.0 code paths (not fully traced) — verify docs still match the artifacts actually emitted.

### Fix before tagging 2.0.0
Add `graph` + `harness` sections to `cli-reference.md`, a Knowledge-Compiler/Harness quick-start to `getting-started.md`, and disambiguate the "graph" term.
