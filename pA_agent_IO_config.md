# Phase A — Governed Agent File I/O Integration

## Fact-Finding, Design, and Implementation Plan

**Scope:** Phase A only — real, contract-scoped agent file read/write capability
**Priority:** P0 / Blocking
**Follow-on rounds:** Phase B — iterative tool loop; Phase C — PLAN.md generation; Phase D — Work Order + Contract authoring; Phase E — D024 QA gate

---

## 1. Executive Summary

The current StackMind CLI contains the security primitives required for governed agent file operations, but the active Harness execution path does not connect the agent turn to those primitives.

The repository currently has:

* a Harness output schema with `modified_files` as filenames and `commands` as command strings;
* a `FileWrite` internal operation type used by the runner for Harness-owned bookkeeping;
* a kernel `ToolGateway` with real `read_file`, `write_file`, `run_command`, and `query_graph` operations;
* contract and workspace enforcement behind that gateway;
* a `ProviderGateway` that already knows how to expose tools to a provider and execute a tool-calling loop;
* a hardened command boundary that rejects shell/interpreter bypasses;
* an active `AgentRunner.run_once()` path that calls the provider directly via `llm_provider.complete(request)`.

The primary architectural defect is therefore not the absence of a secure file-writing primitive.

It is:

> **The active Harness runner is disconnected from the existing governed kernel tool path.**

Phase A must close that gap without weakening the security model.

The desired architecture is:

```text
AgentRunner
   |
   v
Provider / model turn
   |
   +--> read_file(path)
   |
   +--> write_file(path, content)
   |
   +--> run_command(argv)        [existing policy boundary]
   |
   +--> query_graph(query)
   |
   v
ProviderGateway
   |
   v
ToolGateway
   |
   +--> Contract authorization
   +--> Workspace containment
   +--> Sandbox / interpreter policy
   +--> Operation journal
   |
   v
Scratch workspace
```

The model must no longer express source-code creation indirectly through shell redirection.

**File mutation must become a first-class governed operation.**

# 2. Verified Current-State Findings

## 2.1 Harness output does not carry file content

`schemas/harness-output.schema.json` defines fields including:

* `modified_files`: array of filenames;
* `commands`: array of command strings;
* `status`;
* `summary`;
* `report_markdown`;
* other final-result metadata.

There is no file-write payload such as:

```json
{
  "file_writes": [
    {
      "path": "src/app.py",
      "content": "..."
    }
  ]
}
```

The schema also uses:

```text
additionalProperties: false
```

Therefore, adding an undeclared `file_writes` field to the existing Harness decision without changing the schema would be rejected.

### Conclusion

Model-generated source content currently has no first-class transport through `HarnessDecision`.

---

## 2.2 `modified_files` is metadata, not file content

The runner maps the model payload into a tuple of filenames:

```python
modified_files=tuple(
    str(item)
    for item in payload.get("modified_files", [])
)
```

This tells the Harness what files the model claims to have modified.

It does **not** contain the actual content.

The runner subsequently compares the declaration against an observed workspace diff:

```python
declaration_matches = (
    set(observed_task_files) == set(decision.modified_files)
)
```

This distinction is valuable and should be preserved.

### Design rule

`modified_files` remains:

> declarative/result metadata

It must not become:

> the transport mechanism for source-code content.

The authoritative change set should continue to come from the actual workspace.

---

## 2.3 Existing `FileWrite` is Harness-owned bookkeeping

The Harness runner defines an internal operation resembling:

```python
@dataclass(frozen=True)
class FileWrite:
    path: Path
    content: str
    append: bool = False
```

The existing construction sites are associated with Harness-owned persistence such as:

* work-order YAML bookkeeping;
* inbox handoff notices;
* inbox archival;
* Harness reports;
* events/experience records.

These writes are generated by the runner itself.

They are not model-facing file-writing operations.

### Critical distinction

```text
MODEL-ORIGINATED FILE WRITE
    ↓
ToolGateway.write_file()

HARNESS BOOKKEEPING WRITE
    ↓
existing FileWrite / _apply_ops
```

These must remain separate.

---

## 2.4 Active `AgentRunner` performs direct provider completion

The current active execution path reaches:

```python
completion = self.llm_provider.complete(request)
```

The returned response is then converted into the structured Harness decision.

The important observation is:

```text
AgentRunner
    ↓
LLMProvider.complete()
    ↓
HarnessDecision
```

rather than:

```text
AgentRunner
    ↓
ProviderGateway
    ↓
ToolGateway
    ↓
tool call / tool result
    ↓
Provider continuation
```

Therefore, the active agent turn currently does not have access to the governed file tools.

---

## 2.5 `ToolGateway` already provides governed file operations

The kernel already contains a real tool gateway with operations including:

```text
read_file
write_file
run_command
query_graph
```

The existing write path performs the relevant security checks before mutation, including:

1. runtime authorization;
2. contract evaluation;
3. workspace path resolution;
4. workspace containment;
5. actual write;
6. operation journaling.

The workspace implementation also protects against path escapes such as:

```text
../
absolute paths
resolved paths outside scratch root
```

### Conclusion

A new raw filesystem abstraction is not required.

The existing gateway should become the model's mutation boundary.

---

## 2.6 `ProviderGateway` already contains the tool protocol

The repository also contains an existing provider gateway exposing the standard tools:

```text
read_file
write_file
run_command
query_graph
```

It also contains tool execution and loop machinery such as:

```text
execute_tool_call()
run_loop()
```

The existing architecture therefore already supports the conceptual sequence:

```text
provider completion
      ↓
assistant tool call
      ↓
ToolGateway
      ↓
tool result
      ↓
next provider completion
```

### Important architectural rule

**Do not create a second tool-calling architecture.**

Phase A should connect the active Harness runner to the existing:

```text
ProviderGateway
        ↓
ToolGateway
```

path.

---

## 2.7 Existing command hardening must remain intact

The command execution path has already been hardened against interpreter/shell bypasses.

The security boundary rejects patterns such as:

```text
bash -c ...
sh -c ...
cmd.exe /c ...
powershell -Command ...
python -c ...
node --eval ...
perl -e ...
```

The purpose of Phase A is **not** to reopen these mechanisms.

Instead, the architecture changes from:

```text
model wants to write file
        ↓
shell redirection
        ↓
security boundary rejects it
```

to:

```text
model wants to write file
        ↓
write_file tool
        ↓
contract authorization
        ↓
workspace validation
        ↓
safe write
```

The command denylist must remain unchanged.

# 3. Problem Statement

The current execution model approximately behaves as:

```text
Task
  ↓
Context / retrieval
  ↓
llm_provider.complete()
  ↓
HarnessDecision
  ↓
modified_files + commands
  ↓
staged validation / bookkeeping
```

The missing capability is:

```text
Model intent
     ↓
Governed tool call
     ↓
Contract authorization
     ↓
Scratch workspace mutation
     ↓
Tool result
     ↓
Model continues
```

Without this capability, an agent cannot reliably perform normal coding-agent behavior:

```text
inspect existing code
        ↓
reason
        ↓
create/edit file
        ↓
inspect result
        ↓
run permitted command
        ↓
fix issue
        ↓
finalize
```

This is the fundamental blocker for actual Backend/Frontend agent implementation.

---

# 4. Phase A Objective

Implement a first-class governed file I/O path connecting the real StackMind agent turn to the existing kernel tool system.

At completion, an agent must be able to:

1. read existing files;
2. create files;
3. replace file contents;
4. receive tool results;
5. operate entirely inside the governed scratch workspace;
6. have all writes checked against the active contract;
7. have actual changes detected from the workspace;
8. have changes verified before promotion.

The phase must establish:

* real file reads;
* real file writes;
* contract enforcement;
* workspace containment;
* tool result propagation;
* authoritative workspace diffing;
* security regression coverage;
* compatibility with existing Harness bookkeeping.

---

# 5. Non-Goals

Phase A does **not** attempt to implement the complete autonomous coding runtime.

The following remain explicitly deferred:

* sophisticated multi-round agent reasoning;
* advanced patch/diff tools;
* automatic merge/conflict resolution;
* PLAN.md-specific workflows;
* Work Order authoring;
* Contract authoring;
* D024 QA enforcement;
* GitOps policy redesign;
* model-specific prompt optimization;
* broad local-model optimization;
* new shell execution mechanisms.

Those belong to later rounds.

# 7. Target Architecture

## 7.1 Standard tool surface

The model-facing tools should remain:

```text
read_file
write_file
run_command
query_graph
```

The existing gateway already establishes this vocabulary.

Do not create competing mechanisms such as:

```text
file_writes
file_edits
source_blocks
shell_write
code_payloads
```

unless a future architectural decision explicitly requires them.

---

# 7.2 `read_file`

Conceptually:

```json
{
  "name": "read_file",
  "arguments": {
    "path": "src/example.py"
  }
}
```

Execution:

```text
Model
  ↓
ProviderGateway
  ↓
ToolGateway.read_file()
  ↓
RuntimeBoundary
  ↓
Contract authorization
  ↓
ScratchWorkspace
  ↓
Read
  ↓
Tool result
  ↓
Model
```

The model should receive the actual content of the file in the tool result.

---

# 7.3 `write_file`

Conceptually:

```json
{
  "name": "write_file",
  "arguments": {
    "path": "src/example.py",
    "content": "..."
  }
}
```

Execution:

```text
Model
  ↓
ProviderGateway
  ↓
ToolGateway.write_file()
  ↓
RuntimeBoundary
  ↓
Contract authorization
  ↓
ScratchWorkspace
  ↓
Write
  ↓
Journal
  ↓
Tool result
  ↓
Model
```

The model never receives unrestricted filesystem access.

---

# 7.4 Final result semantics

At the end of the agent turn:

```text
actual workspace state
        ↓
workspace diff
        ↓
observed modified files
```

The final `modified_files` field remains useful, but it should be treated as a model declaration that can be compared against actual observation.

The observed workspace remains authoritative.

---

# 8. Schema Decision

## Do not make `file_writes` the primary Phase A protocol

A possible design would be:

```json
{
  "file_writes": [
    {
      "path": "app.py",
      "content": "..."
    }
  ]
}
```

This would technically solve the immediate content-transport problem.

However, it would be inferior to the existing tool architecture because coding agents naturally need:

```text
read
 ↓
reason
 ↓
write
 ↓
observe result
 ↓
read again
 ↓
modify
 ↓
test
```

A batch:

```text
file_writes[]
```

does not naturally represent this interaction.

The repository already contains a tool-call architecture capable of doing it.

### Phase A decision

**Connect the active runner to the existing tool protocol instead of adding `HarnessDecision.file_writes` as the primary mutation mechanism.**

---

## Provider compatibility

If a local provider cannot emit native tool calls, an adapter may translate a provider-specific structured representation into the existing internal tool-call abstraction.

However:

```text
Provider-specific format
        ↓
ToolCallRequest
        ↓
ProviderGateway
        ↓
ToolGateway
```

must remain the boundary.

The adapter must never translate tool calls into shell commands.

---

# A3 — Make model writes governed

Every model-originated file write must terminate at:

```text
ToolGateway.write_file()
```

The model must not directly invoke:

```python
Path.write_text(...)
```

or:

```python
open(..., "w")
```

or:

```python
subprocess(...)
```

to create source files.

Shell redirection is prohibited.

Heredocs are prohibited.

Interpreter-based file creation is prohibited.

---

# A4 — Preserve contract enforcement

Every model write must go through:

```text
active contract
        ↓
authorization
        ↓
workspace validation
        ↓
write
```

Required negative tests include:

```text
absolute POSIX path
absolute Windows path
../ traversal
denied path
read-only contract
path outside allow rule
missing contract
invalid contract
```

Contract denial must fail closed.

---

# A5 — Preserve command hardening

`run_command` remains a separate operation.

These must remain rejected:

```text
bash -c ...
sh -c ...
cmd.exe /c ...
powershell -Command ...
python -c ...
node --eval ...
perl -e ...
```

Phase A must not weaken any existing sandbox/interpreter restriction.

The presence of a legitimate `write_file` tool eliminates the need for command-based file creation.

---

# A6 — Make workspace observation authoritative

Reuse the existing workspace snapshot/diff mechanisms.

Conceptually:

```text
baseline snapshot
        ↓
agent tool operations
        ↓
scratch workspace
        ↓
final snapshot
        ↓
diff
```

Then derive:

```text
observed_task_files
```

from the actual diff.

Compare that with:

```text
decision.modified_files
```

if present.

### Important invariant

```text
model claim
    ≠
authoritative filesystem state
```

The filesystem state wins.

---

# A7 — Tool failure semantics

Tool failures must become structured model-visible results.

Example:

```json
{
  "ok": false,
  "error": "permission_denied",
  "message": "target is outside allowed scope"
}
```

Potential error categories:

```text
invalid_arguments
permission_denied
workspace_escape
file_not_found
write_failed
command_denied
tool_unavailable
```

Use the repository's existing tool-result format where one already exists.

Do not invent a second incompatible result protocol unnecessarily.

---

# 10. File Editing Strategy

Phase A requires only:

```text
read_file
write_file
```

A separate `edit_file` operation is not initially required.

An edit can be represented as:

```text
read_file
    ↓
model reasons over existing content
    ↓
write_file(new complete content)
```

This keeps the initial security surface small.

A patch/diff-based editing tool can be evaluated later after the basic runtime works.

---

# 11. Transaction / Staging Model

The existing staged/verified architecture must remain intact.

Target execution:

```text
1. Load task
2. Load contract
3. Assemble context
4. Establish governed scratch workspace
5. Start provider execution
6. Model requests tool
7. Tool executes in scratch
8. Tool result returns to model
9. Model completes
10. Snapshot scratch workspace
11. Calculate diff
12. Verify contract
13. Validate result
14. Promote verified changes
15. Persist Harness bookkeeping
16. Produce report
```

The model must not write directly into the authoritative live project before verification.

---

# 12. Existing `_apply_ops`

Do not remove `_apply_ops`.

It remains responsible for Harness-controlled persistence.

Examples:

```text
work-order bookkeeping
inbox handoffs
reports
experience records
audit records
```

Model project mutations belong to:

```text
ToolGateway
```

This separation is important because the security requirements are different.

---

# 13. PLAN.md Consequence

After Phase A, PLAN.md does not need its own write subsystem.

Architecture can simply perform:

```text
research
   ↓
write_file("PLAN.md", content)
   ↓
read_file("PLAN.md")
   ↓
final decision
```

Therefore:

> **PLAN.md generation is a consumer of the file-I/O capability, not a separate infrastructure feature.**

This is why Phase A is the true blocker.

# 15. Observability

Every model tool operation should be attributable to:

```text
agent
provider
session
attempt
operation ID
tool name
target path
authorization result
result status
timing
```

For example:

```text
tool: write_file
path: src/app.py
bytes_written: 1482
authorized: true
operation_id: ...
```

Do not automatically duplicate complete source contents into audit logs.

The operation metadata is sufficient unless an existing debugging/audit contract explicitly requires content capture.

---

# 16. Budget and Safety Controls

Tool-enabled execution must remain inside the existing contract/resource budget.

Ensure:

* tool calls count toward the same model/token budget;
* the provider cannot bypass `max_tokens`;
* tool execution has a bounded number of calls;
* runaway tool loops have a deterministic stop condition;
* cancellation remains possible.

Phase A only needs a minimal bounded mechanism.

More sophisticated agentic loop controls belong to Phase B.

# 18. Error Handling

The system must distinguish:

```text
provider failure
tool argument failure
authorization denial
workspace escape
tool execution failure
verification failure
contract failure
```

For example:

```text

```

must not look like:

```text

```

The model should receive meaningful tool errors so that a capable provider can correct its next action.

# 23. Risks

## R1 — Duplicate Runtime Architecture

### Risk

Creating another file-write subsystem beside ToolGateway would create multiple security boundaries.

### Mitigation

Reuse:

```text
ProviderGateway
ToolGateway
RuntimeBoundary
ScratchWorkspace
```

---

## R2 — Contract Mismatch

### Risk

Harness-level authorization and kernel-level authorization could disagree about which files are allowed.

### Mitigation

Make the kernel authorization path authoritative for actual tool operations.

Explicitly reconcile Harness contract loading with the kernel `AgentContract`.

---

## R3 — Workspace Mismatch

### Risk

The provider writes into one workspace while verification observes another.

### Mitigation

One model-facing scratch workspace per attempt.

All:

```text
read
write
snapshot
diff
verification
```

must operate against the same model workspace.

---

## R4 — Local Model Tool-Call Reliability

### Risk

Local models may sometimes produce malformed tool calls.

### Mitigation

Use:

* strict argument validation;
* structured tool errors;
* bounded tool execution;
* deterministic failure;
* explicit final status.

Do not solve malformed tool calls by restoring shell execution.

---

## R5 — Accidental Live Writes

### Risk

An implementation convenience could call:

```python
Path.write_text()
```

against the real project.

### Mitigation

Enforce the architectural invariant:

> **No model-originated mutation may bypass ToolGateway.**

Add an integration test proving that the authoritative project remains unchanged until verification/promotion.

---

# 24. Architectural Invariants

These invariants must remain true after Phase A.

```text
I1  Model has no direct filesystem authority.

I2  Model-originated writes use ToolGateway.write_file.

I3  ToolGateway writes only inside ScratchWorkspace.

I4  RuntimeBoundary authorizes every governed operation.

I5  Contract rules are fail-closed.

I6  Shell/interpreter denylist remains enforced.

I7  Verified workspace diff is authoritative.

I8  Harness bookkeeping remains separate from model file mutation.

I9  Existing ProviderGateway tool protocol is reused where possible.

I10 Token/budget accounting remains attributable to the same agent attempt.

I11 The authoritative project is not modified by model tools before verification.

I12 `modified_files` is metadata/verification information, not a file-content transport.

I13 No shell/heredoc/interpreter fallback is introduced for source-file creation.

I14 Tool failures are visible to the model as structured results.

I15 All model-originated operations are attributable to an agent/session/attempt.
```

# 25. Final Implementation Directive

Implement **Phase A only**.

Start with repository fact-finding.

Do not modify Phase B, C, D, or E behavior except where a minimal compatibility change is mechanically required by Phase A.

Do not add a shell-based fallback.

Do not create a parallel file-write runtime if the existing:

```text
ProviderGateway
        +
ToolGateway
```

can be connected to the active `AgentRunner`.

Do not turn `modified_files` into a source-code payload.

Do not treat a model declaration as proof that a file was modified.

The success condition is not:

> "The model claims it modified files."

The success condition is:

> **The real StackMind agent turn can inspect and modify actual project files through the existing governed tool boundary, with contract authorization, scratch isolation, observable diffs, and verification preserved end-to-end.**

Phase A is complete only when a real end-to-end test can demonstrate:

```text

    ↓

    ↓
read_file
    ↓
actual source content
    ↓
write_file
    ↓
ToolGateway
    ↓
Contract authorization
    ↓
ScratchWorkspace
    ↓
actual file mutation
    ↓
workspace diff
    ↓
verification
    ↓
promotion
    ↓
final Harness result
```

Anything less is not a complete implementation of Phase A.
